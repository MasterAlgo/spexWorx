SpexWorx Agents Guide v4.0

Compiling Human Intent into Navigable Information Systems

Working Draft

Preface

Every software platform carries an implicit philosophy.

Some believe software begins with databases.

Some begin with objects.

Others begin with web pages, REST APIs, components, or services.

SpexWorx begins somewhere else.

It begins with human intent.

A human rarely thinks in terms of tables, foreign keys, indexes or REST endpoints.

Instead they say things like:

"I'd like to organize my music."

"I need something to manage our veterinary clinic."

"Can I keep research papers together with my notes?"

These wishes already contain the architecture.

The challenge is discovering it.

This guide describes how a coding agent—or a human architect—transprets a free-form wish into a navigable information system.

The purpose of the guide is not to explain AppML syntax.

The purpose is to teach architectural reasoning.

AppML is merely the language used to express the final result.

Chapter 1
The SpexWorx Philosophy
1.1 Software is an Information Space

Traditional software often treats an application as a collection of forms.

Login

↓

Customers

↓

Edit Form

↓

Save

SpexWorx treats an application differently.

An application is an information space.

Users move through information.

Navigation becomes the primary activity.

Editing becomes secondary.

Imagine entering a museum.

Nobody begins by asking

"Where is the database?"

Instead they ask

"Where should I go first?"

Applications are no different.

Good applications answer

"Where do I go next?"

rather than merely

"What fields should I edit?"

Navigation therefore becomes a first-class architectural concept.

1.2 Persistent Objects

Everything meaningful inside an application eventually becomes a persistent object.

Examples

Patient

Customer

Invoice

Book

Photo

Album

Recipe

Project

Experiment

Persistent objects have identity.

They survive application restarts.

They can participate in relationships.

They can contain rich media.

They can accumulate history.

Transient concepts usually do not become persistent objects.

Examples

Search results

Clipboard

Import session

Wizard page

Temporary filter

These exist only while the application is running.

1.3 Ownership

One of the most important architectural questions is

Who owns this object?

Ownership determines navigation.

Ownership determines hierarchy.

Ownership often determines lifecycle.

Example

Customer

↓

Orders

↓

Order Items

Deleting a customer may eventually remove every order.

Deleting an order removes its items.

Ownership therefore forms a hierarchy.

Contrast this with

Order

→ Product

→ Employee

→ Warehouse

Products are not owned by Orders.

Employees are not owned by Orders.

Warehouses are not owned by Orders.

These are references.

Ownership and reference must never be confused.

1.4 Navigation before CRUD

CRUD is important.

Navigation is more important.

A CRUD-oriented system asks

How can users edit records?

SpexWorx asks

How do users naturally discover information?

These questions produce different architectures.

Example.

CRUD thinking produces

↓

↓

↓

↓

Finding becomes more valuable than editing.

1.5 Information is Multi-dimensional

Folders assume every object belongs to one place.

Reality rarely behaves this way.

A song may simultaneously belong to

Which one is its real location?

1.6 Rich Objects

Modern information rarely consists of text alone.

A single object may include

Description

Image

PDF

Audio

Voice recording

Video

Collaborative notes

SpexWorx therefore treats media as part of the object itself rather than external attachments.

Media is not an afterthought.

Media participates naturally in navigation.

1.7 Backend by UI

Most frameworks begin with backend code.

Then APIs.

Then UI.

SpexWorx deliberately reverses this process.

The developer first models the information space.

The runtime derives persistence, navigation and interaction directly from that model.

The UI therefore becomes a declarative description of the application rather than a thin layer over handwritten backend code.

This approach does not eliminate programming.

Instead it moves programming toward behavior rather than infrastructure.

1.9 The Role of AppML

AppML is not the application.

It is not the database.

It is not the runtime.

AppML is an Intermediate Representation (IR).

Human Wish

↓

Architectural Reasoning

↓

Domain Model

↓

Navigation Graph

↓

AppML

↓

Runtime

↓

Running Application

AppML exists because both humans and runtimes benefit from an explicit architectural description.

It separates reasoning from execution.

1.10 The Prime Directive

Every decision made by the compiler must satisfy one principle:

Represent the user's world as naturally as possible.

Not the programmer's world.

Not the database's world.

Not SQL's world.

Not XML's world.

The user's world.

If the generated navigation feels obvious to someone familiar with the domain, the compilation has succeeded.

If users constantly ask

"Where do I find that?"

the architecture should be reconsidered before adding more features.

"Architecture describes the world. Components express that architecture."

Architecture should never be influenced by implementation.

A compiler must first understand what the user is describing.

Component selection is therefore not a creative activity.

Chapter 6
AppML — The Application Modeling Language

"AppML is not a programming language. It is an architectural language."

6.1 Purpose

AppML exists for one purpose:

To describe an information system in a form that can be compiled into a running application.

AppML intentionally avoids describing algorithms.

Instead it describes

information
navigation
ownership
relationships
presentation
behavior

The runtime supplies implementation.

6.2 Design Principles

Every AppML document should satisfy five principles.

Declarative

AppML describes

what exists

never

how it works

Example

<table name="Artists">

Good.

for(eachArtist)

Impossible.

Algorithms belong elsewhere.

Deterministic

The same AppML should always produce the same application.

Compilation should never depend on execution order.

Human-readable

Architects should comfortably read AppML.

Developers should comfortably review AppML.

LLMs should comfortably generate AppML.

Stable

Small architectural changes should produce small XML changes.

The compiler should not rewrite unrelated sections.

Extensible

New components should extend the language.

They should not require redesigning the language.

6.3 The Application

Every document begins with exactly one application.

<application
    name="Music Archive"
    user-port="8081"
    dev-port="8082"
    app-resources-path="..."/>

The application defines

identity
runtime ports
resource location
global configuration

Nothing more.

Applications consist of components.

Components are persistent architectural objects.

identity

behavior
relationships
6.5 Identity

Most language specifications define syntax first and meaning second.

We've done the opposite.

We defined:

Intent

Only then did we reach XML.

I think that's actually the right order for SpexWorx. It teaches an agent that AppML is a consequence of architectural reasoning, not the starting point. Chapter 8
Architectural Heuristics

"Rules guarantee correctness. Heuristics guide judgment."

8.1 Introduction

No specification can anticipate every domain.

The compiler must therefore employ heuristics.

A heuristic is not a rule.

A heuristic is a preference that has repeatedly proven useful across many applications.

Rules should always be obeyed.

Heuristics should be considered.

The compiler should understand the difference.

8.2 Rules versus Heuristics

Every component shall have a unique identifier.

Violation is an error.

Prefer shallow hierarchies over deep hierarchies.
